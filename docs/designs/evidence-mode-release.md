## Problem Statement

An AI coding agent's spend is invisible until the invoice arrives. The number
the provider bills is the only ground truth, and nobody reconciles against it:
every "savings" dashboard in this category computes a figure from a *price
sheet*, which is an estimate the operator supplied.

A landscape scan of eight comparable open-source LLM gateways on 2026-10-21
(see the table below) found that routing to a cheaper model, per-key budgets,
and savings dashboards are all commodity features. Reserve-then-settle
admission — the pattern that actually stops money leaving the account — is the
documented industry fix for the check-then-act race, and every serious
competitor ships some form of it. **None of the eight reconciles a savings
figure against what the provider actually billed.**

Tamias is a local proxy that sits between an agent and a metered provider,
speaks the OpenAI chat-completions API, and does four things: it produces a
**receipt** (per-request token usage, cache reads, latency, status, computed
cost, and the reason for every routing decision, in a local SQLite file),
**caps** spend (per-key budgets with reserve-then-settle admission, per-model
sub-caps, RPM/TPM windows, 402 refusals that never reach the provider), can
**cut** spend (a router that rewrites the model to a configured cheaper target
on turns it judges safe), and can **prove** whether any of that saved money
(offline harnesses that make the savings arithmetic falsifiable, and a
ledger-based A/B that reads the provider's own `GET /api/v1/key` `data.usage`
around each arm and reports `saving = X − Y`).

The problem this design addresses: **a cost claim nobody can check is not a
cost claim.** The release should make the receipt checkable, make the cap
**bounded and auditable** (never silently exceeded beyond a stated bound, with
the four qualifications listed under Premise 3), and make the routing claim
either provable or explicitly withdrawn.

## What Makes This Cool

The maintainer's answer to "what is the coolest version of this" was **"all of
them"** — the receipt, the cap, the cut and the proof are one product, not
four. The entry point is the receipt; the other three are what you can do with
it.

The sharpest version of that is **Evidence Mode**: one command runs a real task
in three arms — strong/off, adaptive/active, and direct static-cheap — against
a pass/fail oracle, reads the provider's ledger around each arm, verifies each
arm's identity by the contract below, and **recommends active routing only
when it beats both baselines** under a preregistered decision rule. It stores
no prompt or response text: only a spec hash, the arm assignment, ledger
deltas, routing coverage and the outcome.

That makes Tamias a decision system rather than another cheaper-model router,
and it is the one position in the landscape scan nobody occupies. Two further
properties most competitors break: **no prompt or response text is ever
written to disk** (RelayPlane logs system prompt previews, user messages and
response previews), and **the arithmetic can go negative** — the realised
saving is shown as a loss rather than clamped at zero.

## Constraints

- **No spend.** The owner has no provider credits and will not spend until
  final testing. Every design decision that costs money is deferred and
  refusal-gated, not executed.
- **Irreversible operations are owner-gated:** tag deletion, history rewrite,
  publishing a release.
- **Single maintainer.** Everything must be reviewable by one person.
- **A 992-test package with a public API surface.** New public surface is a
  cost, not a free choice.
- **The public tree was deliberately cleaned.** Maintainer-only files (design
  spec, benchmark task fixtures, demo collateral) are untracked and live in a
  git-excluded `.local/` directory, with restore instructions. **That
  exclusion is currently local and uncommitted** — it lives in
  `.git/info/exclude`, so a fresh clone has no such rule, nothing in `.local/`
  is tracked, and the restore instructions, the benchmark task fixtures, the
  oracle implementations and the private claims ledger exist in exactly one
  place on exactly one machine. Worse, the runner's own reset step could
  delete `.local/`. Before release one: `.local/` is added to the **tracked**
  `.gitignore` so the exclusion travels with the repository, the restore
  instructions are tracked, and the directory is put under an off-machine
  backup or a private remote.
- **The headline is unmeasured.** No paid, non-zero-rate run has ever been
  reconciled. The savings *arithmetic* is verified against authored rates; the
  *rates* are not real; no dollar figure has met a provider invoice.
- **A `:free` model bills $0**, so the ledger does not move on free models and
  no money measurement is possible without a paid model pair.

## Premises

1. **Routing to a cheaper model is now table stakes, not a differentiator.**
   LiteLLM's "Auto Routing" and "Lowest-cost routing", RelayPlane's task-aware
   routing and auto-downgrade, and Routerly's nine routing policies all ship
   it. *Confirmed by the maintainer.*
2. **The unfilled position is a *preregistered routing claim* reconciled
   against the provider's own record.** Reconciliation itself is **not** empty:
   LiteLLM ships `GET /spend/capture_rate`, which "compares the spend LiteLLM
   captured for a provider against that provider's own bill" by reading the
   OpenAI Organization Costs API, and five commercial FinOps products sell
   "the invoice and your estimate, with the delta". What none of them does is
   preregister a *routing* claim and then settle it against billed truth. That
   narrow claim is the position; the earlier broad claim was false and is
   withdrawn. *Corrected after independent review; see the Review record.*
3. **"Tamias cannot bypass the budget cap" is the one guarantee true today.**
   The ceiling is enforced by reserve-then-settle before the request is
   forwarded; **five numbered qualifications travel with it, and they are
   quoted verbatim wherever the guarantee is stated** — this premise, the
   contract, `README.md`, `docs/BUDGET.md` and `docs/VERIFICATION.md` must
   carry the same five sentences in the same order, so a reviewer counting
   them cannot accept four of five:
   **Q1** a request that exhausts a limit may overshoot by `actual − ceiling`,
   because the reserve is a flat ceiling; **Q2** a model the sheet cannot price
   is refused under a money limit, because an unknown cost cannot be spent
   against; **Q3** the count-only passthrough route is never *priced*, but it
   **is** gated: a key carrying a limit is refused **403** when the passthrough
   body names a model (`proxy.py:_unmetered_forbidden`), so the cap holds on
   every metered route and on the passthrough route for any body that names a
   model, and the route stays open only for bodies that name no model; **Q4**
   the guarantee is about **the cap**, not about the proxy being unbypassable —
   the proxy is a local process the operator owns, and auth is opt-in, so the
   agent can be pointed straight at the provider instead; **Q5** the cap is
   enforced against the cost computed from the
   price sheet, not against the provider's bill. The reservation settles the
   computed figure (`proxy.py:984` → `pricing.compute_cost`, then
   `budget.py:_measurement`); the provider's own reported cost is stored
   separately in `provider_cost_usd` and is never settled against, so a stale,
   missing or wrong rate makes the cap and the bill diverge. It is a necessary
   control, not a selling point. *Confirmed, and (e) was added after
   verification against the source.*
4. **Not storing prompt or response text is a real differentiator** that most
   competitors break. *Confirmed.*
5. **A null or negative routing result does not sink the roadmap**, because the
   receipt and the cap stand on their own in the first release, and the
   reconciliation machinery — which is the point at stake — arrives with the
   runner in the second release. *Confirmed.*
6. **Distribution beats features here.** Tamias cannot out-feature LiteLLM, so
   it must win on a narrow position and on being usable by one person in five
   minutes. *Confirmed.*

## The experiment contract

This is the part that has to be exactly right, because the whole cost-saving
aim rests on it.

### What the ledger measures, and in what unit

**Two instruments, and the better one is already in the repo.**

**Primary: per-request billed cost.** `scripts/reconcile_live.py` already
reads `GET /api/v1/generation?id=<generation-id>` → `data.total_cost` — the
provider's billed amount **for that specific request** — and the request log
already stores the `generation_id` column that carries it. Per-request billed
truth is exact where a cumulative counter is approximate: attribution needs no
bracket, no settle window and no concurrency argument, because each request's
cost is known when that request is known. A refund stops invalidating an arm,
a small delta stops rounding away, and "the arm made no requests" gains a
second, independent proof (no generation ids ⇒ no requests). **One capture gap
must close first:** chat-completion response-id placement is unverified, so the
id has to be captured and confirmed for the chat route.

**Cross-check: the cumulative counter.** `GET /api/v1/key` → `data.usage`.
OpenRouter's own field description is *"Total OpenRouter credit usage (in USD)
for the API key"*
(<https://openrouter.ai/docs/api/api-reference/api-keys/get-current-api-key>).
**The counter is a dollar amount, not a token count**, so no price sheet is
reintroduced anywhere in the comparison. It is no longer the primary
instrument; it is the **falsification check** the plan actually wants: the sum
of an arm's per-request billed costs must equal the counter's movement over
the same window. That equality is a stronger statement than a single bracket,
and its failure is a hard error rather than a statistical wobble.

Because the primary instrument is per-request, most of the attribution
conditions below exist only for the cross-check. They are retained, not
deleted, and they are marked as governing the cross-check. Three properties of
the counter still shape it:

- `usage` is **cumulative over the key's lifetime** and is the correct bracket
  counter. `usage_daily`, `usage_weekly` and `usage_monthly` reset at UTC
  period boundaries and are therefore unusable as a bracket counter across a
  boundary.
- `byok_usage` is a **separate** figure for external BYOK spend and is not
  included in `usage`; a run that uses BYOK providers is not measuring what it
  thinks it is, so the runner refuses a spec that mixes them.
- A **decrease** in `usage` during a bracket means a refund or an adjustment,
  not a spend, and invalidates the arm.

### Arm identity: how each arm proves it was the arm it claimed to be

The three arms are not symmetric, and their identity cannot be proven by the
same artifact. The `static_cheap` arm **bypasses Tamias entirely**, so it
produces no Tamias request-log row; pretending otherwise is how a run would
claim an identity it never had.

**Every arm has a runner-side record, independent of Tamias.** The runner
records, for each arm, the number of requests it made outbound, the model it
asked for, and the wall-clock window. This record exists for all three arms,
including the bypass arm, and it is what the ledger attribution check
reconciles against. The Tamias request log is an *additional* evidence source
for the two proxied arms, never the only one.

| Arm | What it does | Identity proof | Invalid when |
| --- | --- | --- | --- |
| `off` | The agent requests the strong model; the proxy is in `off` mode and forwards it unchanged. | The proxy ran in `off` mode (the request log's `router_mode` column says so) **and** every row's `model_requested` is the spec's strong model **and** the runner's outbound record shows at least one request. | Any row shows `model_used != model_requested`; **or** the runner's outbound record shows zero requests (a mis-wired agent that never called out — the arm would otherwise pass vacuously); **or** the request count in the log and in the runner's record disagree. |
| `active` | The agent requests the strong model; the proxy is in `active` mode and may rewrite to the spec's cheap target. | The proxy ran in `active` mode (the request log's `router_mode` column says so) **and** every rewritten row targets the spec's declared target (no other model was used) **and** the runner's outbound record shows at least one request. | A rewrite went to a model other than the declared target; **or** the runner's outbound record shows zero requests (a mis-wired agent that never called out — the arm would otherwise pass vacuously, and a zero-cost arm is exactly the shape that separates in `active`'s favour); **or** the request count in the log and in the runner's record disagree. |
| `static_cheap` | The agent requests the cheap model directly and **never traverses Tamias**. | (i) the spec's recorded model for this arm is the cheap model; (ii) the runner's outbound record shows the cheap model was the one asked for, with at least one request; (iii) **zero** Tamias request-log rows attributable to the arm's session id; (iv) the ledger moved by a non-zero amount during the repetition's bracket. | Any one of the four missing, including zero requests in the runner's outbound record. |

**The no-request floor applies to all three arms.** An arm whose runner-side
outbound record shows zero requests is `INVALID`, without exception.

**Identity is separate from effect.** A correctly wired `active` arm in which
the router judged no turn safe is a **valid** arm with routing coverage `0.0`.
It is not invalid, and it is not excluded: that is the conservative behaviour
the product's safety story depends on, and penalising it would erase exactly
the null result this design commits to publishing. Whether a task set in
which the router never fires is *informative* is a separate, preregistered
condition on the task set — a minimum routing-coverage floor — not a
per-arm validity rule. A task below the floor is reported as **"the router
judged no turn safe"**, which is a finding.

**Routing coverage** is defined numerically: for a proxied arm,
`rewritten_requests / total_requests` in that arm's session, where *rewritten*
means `model_used != model_requested` in the request log. It is recorded in
the run record. For `static_cheap` it is not applicable (the arm is
`bypassed`), and the run record says so rather than recording a misleading
`0.0`.

### Ledger attribution: what makes the provider's counter attributable

A difference between two reads is only attributable to the work bracketed
between them if the conditions below hold. The runner performs all of them
and records each one's result in the run record.

1. **Key isolation.** The run uses a provider key used by nothing else. The
   runner records the key's `label` (never the key) so a misconfiguration is
   visible without exposing a credential.
2. **No concurrent traffic (pre-arm only).** The counter is read **twice in quick succession
   immediately before** the repetition, and the two readings must be **equal**.
   Any movement between them is another workload using the key, it falls inside
   the measured bracket, and it would be silently attributed to the repetition
   — so the repetition is **invalid**. The runner requires the *previous*
   repetition's counter to have settled before the next bracket opens, so a
   late-arriving update of the previous repetition's own requests is not
   mis-diagnosed as concurrent traffic. **The pre-arm equal-read rule is the
   only place that treats inter-read movement as concurrent traffic.**
3. **Reconciliation against the runner's own record.** The ledger delta for
   the repetition must be attributable to the requests in the runner's outbound
   record for that repetition: the delta must be non-zero whenever the
   repetition made requests, and the runner's per-repetition request count and
   the request count observed in the Tamias log for that repetition's session
   must agree for the two proxied arms. A delta that cannot be attributed to
   the repetition's own requests invalidates it.
4. **Settlement is an observation of *movement*, not of stillness — and this
   governs the post-arm read.** The provider's counter may be delayed or
   batched, and **a batched counter is stationary before the batch lands**. 
   **Precedence:** condition 4 **governs the post-arm read**. After the last
   response, the counter enters a **settle loop**: re-read until the counter
   stops moving across two consecutive reads, or the preregistered settle
   window expires. A difference between the two post-arm readings is the
   counter settling, not concurrent traffic, and it is **never by itself**
   an invalidity. **If the counter is still moving when the settle window
   expires, the repetition is `INVALID` with the distinct code
   `ledger.unsettled`** — not "settled at zero". The run records **two**
   fields, not one: `counter_moved` (bool) and `settle_seconds`, so a
   never-moved counter is visibly different from a fast one. A fake-clock test
   pins it: the counter increments in two batches, the first landing after the
   settle window opens. The ledger delta is the settled value minus the pre-arm
   value. **The post-arm read has no "must be equal" invalidity rule** — that
   rule applies only to the pre-arm read under condition 2. The run records how
   long the counter took to settle, so a provider whose counter is slow is
   visible rather than silently mis-priced.
5. **A negative delta is a refund, not a saving.** If the settled value is
   **below** the pre-arm value, the counter was adjusted (a refund or a
   credit), and the repetition is **invalid** — a negative ledger delta must
   never lower an arm's measured cost, which is the flattering direction for a
   promotion. The "never clamp" rule applies to the **comparison between arms**,
   not to a negative ledger delta itself.
6. **The passthrough qualification is stated accurately and tested.** The
   passthrough route is never *priced*, and it is **gated**: a key carrying a
   limit is refused **403** when the passthrough body names a model
   (`proxy.py:_unmetered_forbidden`). The route stays open only for bodies
   that name no model, which carry no model cost. The guarantee therefore
   reads: **the cap holds on every metered route, and on the passthrough route
   for any body that names a model.** The executed test list must cover both
   halves — a 403 on a model-naming passthrough under a budgeted key, and the
   open route for a model-less body. An earlier draft of this document said
   the route was "never budget-gated"; that was wrong, and it is corrected here
   against `proxy.py`.
7. **Failure behaviour.** A repetition whose attribution check fails is marked
   `INVALID`. A task with any `INVALID` repetition is excluded from the
   comparison. The **excluded-fraction threshold applies to the run as a
   whole**: if the fraction of excluded tasks exceeds the preregistered
   threshold, the run's verdict is `INDETERMINATE` — not a result — and no
   promotion happens. Every invalid repetition is named in the report with the
   check that failed, so exclusions are never silent.

### The decision rule: what "beats" means

Preregistered before the run, and part of the spec the run is bound to. The
two-arm formula and the three-arm comparison are the same instrument at
different widths, and both are stated so they cannot be confused:

- **Two-arm form** (what `credit_ab_check.py` already computes): for the pair
  (off, active), `saving_vs_off = X_off − X_active` where each `X` is a
  ledger delta. Generalised to the third arm:
  `saving_vs_off = X_off − X_active` and
  `saving_vs_static = X_static − X_active`. A negative value is a loss and is
  reported as a loss, never clamped.
- **The claim under test.** The **null hypothesis** is that *adaptive routing
  does not beat simply pinning a cheap model in the agent's own config*.
  Beating `static_cheap` is what Evidence Mode must show; beating `off` alone
  would not show that Tamias adds anything over the trivial alternative.
  Throughout this document the null hypothesis means exactly that and nothing
  else.
- **Repetition structure, and how it connects to the measurement.** Each task
  is run **k times per arm**, with `k` preregistered in the spec alongside the
  assignment unit and the task count. **Each repetition is a separate
  execution** with its own session id, its own pre-repetition double read, its
  own settle loop, its own settled ledger delta, and its own runner-side
  outbound record. The k observations of a (task, arm) cell **are** those k
  settled deltas, and a task's per-arm range is the `[min, max]` of them.
  `k` is the repetition factor, and it is what makes a range exist at all; a
  single observation per cell has no range to compare. The count-agreement
  check in the attribution contract is **per repetition**, not per cell.
- **Ordering control.** The k repetitions of a task are run **across the arms
  in an alternating or randomised order** so that provider drift does not
  favour one arm. The order is **preregistered** as part of the assignment
  unit, so it is part of the spec the run is bound to and cannot be changed
  after seeing a result.
- **Repetition structure and its mapping to measurements.** Each task is run
  **k times per arm**. For each repetition `(task, arm, repetition)`, the
  runner creates a **separate execution** with its **own session id** (one
  database per `(task, arm, repetition)`, each with its own salt; two tests
  pin that two repetitions yield different session ids and that the bypass
  arm's session id has zero rows), its **own pre-arm double read**, its **own
  settle loop**, its **own settled ledger delta**, and its **own runner-side
  outbound record**. Each (task, arm) cell holds **k observations** — those k
  settled deltas — and the per-arm range is `[min, max]` of them. The
  count-agreement check in the attribution contract compares the **runner's
  per-repetition outbound count** with the **Tamias log's per-repetition count**
  for that repetition's session (not a cell total). A single bracket covering
  the whole cell cannot produce k observations; each repetition is measured
  independently.
- **Per-task separation.** A task is *separated in favour of `active`* against
  a baseline when the arms' observed ranges do not overlap and the gap
  exceeds the floor: `baseline.max − active.min > MDD`, where **MDD is the
  preregistered minimum detectable difference**, derived from the offline
  rehearsal's observed per-task variance. Overlapping ranges are not
  separation and are reported as "unseparated", never as a tie.
- **The aggregate statistic** is the **median across counted tasks** of the
  per-task median cost, for each arm. The decision is never made on pooled
  totals, because task-level variance dominates.
- **Counted task.** A task is *counted* when it is in the preregistered task
  set and none of its arms was `INVALID`. The excluded-fraction threshold is
  a **run-level** rule: if the fraction of excluded tasks exceeds the
  preregistered threshold, the **run's verdict is `INDETERMINATE`** — not a
  per-task removal rule. No individual task is removed "by the
  invalid-task threshold"; the only per-task exclusion is that a task with
  any invalid arm is not counted.
- **Oracle failures block promotion; they do not remove evidence.** A task
  whose oracle failed in any arm **stays in the comparison** and **fails** the
  "oracle passed in every arm of every counted task" condition, so the run
  cannot return `PROMOTE`. It is not excluded, because excluding it would be
  survivorship bias: the tasks an oracle failure identifies are precisely the
  tasks where the cheap model underperformed, and discarding them would let the
  run report a smaller `active` cost by throwing away the evidence against it.
  The run record names the failing arm and the oracle's exit code, and the
  published result reports the count of oracle-failed tasks separately.
- **The routing-coverage floor.** The floor applies **over the task set**, not
  per task: the aggregate routing coverage across the `active` arm's counted
  repetitions must be at least the preregistered floor for the run's verdict
  to be `PROMOTE` or `DO NOT PROMOTE`; **if the aggregate falls below the
  preregistered floor, the verdict is `INDETERMINATE`**, because a run in
  which the router barely fired cannot support a conclusion about the router
  either way. Individual tasks with zero rewrites remain **counted and valid**
  — they are reported as "the router judged no turn safe", which is a finding,
  and they are not excluded. A task set below the floor does **not** remove
  individual tasks by that rule; it makes the **run** `INDETERMINATE` (the
  run-level threshold).
- **The verdict**, on the counted task set, with **INDETERMINATE taking
  precedence** over `DO NOT PROMOTE` whenever either of its conditions holds:
  - `INDETERMINATE` when **any** repetition in the preregistered task set was
    `INVALID` — a dropped measurement is never reported as evidence that
    adaptive routing does not work — **or** the preregistered sample size is
    too small to separate the two closest arms at the MDD, **or** the
    preregistered fraction of excluded tasks exceeds the threshold, **or** the
    aggregate routing coverage is below the preregistered floor. The run
    reports its power estimate rather than a verdict it cannot support. The
    excluded-fraction threshold is a **run-level** rule that yields
    `INDETERMINATE` (not a per-task removal rule).
  - `PROMOTE` only if **all** of: the median per-task cost of `active` is
    lower than the median of `static_cheap` **and** lower than the median of
    `off`; at least two thirds of the counted tasks are separated in
    `active`'s favour against **both** baselines; the oracle passed in every
    arm of every counted task; and **no task in the preregistered task set was
    excluded as `INVALID`** (impossible by the counted-task definition, but
    stated to make the gate explicit).
  - `DO NOT PROMOTE` otherwise, provided **neither** `INDETERMINATE` condition
    holds. **The null hypothesis was not rejected. This is a publishable
    result**, not a failure of the run, and the trivial alternative winning is
    a finding about the category, not about the tool. The three verdicts are
    mutually exclusive by this precedence.
- **Ties and negatives are reported as found.** An arm whose cost is higher
  is reported as higher; the report never clamps **the comparison between
  arms** — a negative saving is a real result. This does not license a
  negative *ledger delta*: a settled value below the pre-repetition value is a
  refund and invalidates the repetition, per the attribution contract.

### The execution contract: what actually runs the task

The router rewrites model names **inside LLM requests**, so the executor must
be an LLM-driven agent. The runner does **not** embed an agent.

- **Executor: the operator's own agent, invoked as a command.** The runner
  reuses the pattern `tamias run` already uses: it starts a proxy (or uses a
  running one), injects `OPENAI_BASE_URL` and `ANTHROPIC_BASE_URL` into the
  agent's environment, and runs the agent command with a fixed prompt. The
  agent's code is not part of Tamias and is not this design's concern; what
  the runner owns is the arm, the bracket, the reset, the oracle and the
  record.
- **A route-capability matrix, because one route cannot carry the `active`
  arm.** The Responses route is meter-only and never rewrites, and it does
  **not** write `router_mode` today, so every `/v1/responses` row carries
  `router_mode = NULL` and the identity proof can never be satisfied for an
  agent that speaks it. Two changes: **the Responses route writes
  `router_mode`**, and the contract states that **`off` and `static_cheap`
  work on any route while `active` requires a rewriting route**
  (`/v1/chat/completions` or `/v1/messages`). The runner **refuses a spec
  whose declared adapter targets a non-rewriting route for the `active` arm**,
  with `arm.identity_mismatch`. **E5 — a mixed-route agent.** The spec
  declares the expected route set per arm; rows are filtered by `route`, and
  the arm fails only for rows on a *rewriting* route, with the route mix
  reported in the run record.
- **The per-arm model contract is typed and implementable, not a sentence.**
  Today `tamias run` injects only `OPENAI_BASE_URL` and `ANTHROPIC_BASE_URL`
  (`cli.py:1613`); it does not control an arbitrary command's model
  selection, so "the agent is configured with the cheap model" is not a
  contract an arbitrary command can satisfy. The runner therefore supports
  **named agents with documented adapters**, each adapter specifying how the
  arm's model is set (environment variable, config file field, or CLI flag)
  and how the arm is undone afterwards. An arm with no adapter is refused
  before it spends anything, not silently run with the wrong model. The
  adapters ship for the agents this project already documents.
- **Model-target injection differs per arm, and that is the point:**
  `off` — the agent is configured with the strong model and the proxy runs in
  `off` mode. `active` — the agent is configured with the strong model and the
  proxy runs in `active` mode with the spec's cheap target, so the rewrite is
  the proxy's doing. `static_cheap` — the agent is configured with the cheap
  model and **the proxy is not in the path**, so no rewrite is possible and
  the arm measures the cheap model on its own terms.
- **Oracle interface:** a command whose **exit code** is the verdict. The
  runner records the exit code and the last line of output, and records a
  content hash of the task's working tree after the run. The oracle's
  implementation and its task fixtures live with the task, not in the package.
- **The session and database layout, stated — the contract depends on it.** A
  session id is a salted digest of the credential, the system text and the user
  text (`session.py:derive_session_id`), and the salt is **per database**. The
  contract runs the *same* command with the *same* credential and a *fixed*
  prompt in every arm, so a single log would give every arm and every
  repetition **the same session id**: the bypass arm's "zero rows attributable
  to its session" check would see the other arms' rows, and the per-repetition
  count agreement would not be computable at all. **The layout is therefore: one
  database per `(task, arm, repetition)`, each with its own salt, and the
  runner reads each repetition's database and aggregates.** Two tests pin it:
  two repetitions of the same task in the same arm yield **different** session
  ids, and the bypass arm's session id has **zero** rows in the log.
- **Repo reset — and the runner owns the path it resets.** The runner creates
  the worktree itself under a directory it owns, records the absolute path, and
  **refuses to run `git reset` or `git clean` against any path it did not
  create**. Inside its own worktree it uses `git clean -fd` unless the spec
  opts into `-x` explicitly. `git clean -fdx` deletes untracked **and ignored**
  files — including `.local/`, `requests.db` and any `.env` — so it is a last
  resort behind an explicit opt-in, and it is added to this project's own
  `AGENTS.md` as prohibited outside the runner's sandbox. A `--dry-run` mode
  prints the planned `git` commands first. The revision, the worktree path and
  the post-reset `git status --porcelain` are recorded. A task that cannot be
  reset to a pinned revision is not eligible.
- **Where the code lives:** the runner module and the spec schema are
  **public**; the task fixtures, the oracle implementations and the sample
  task set are **maintainer-private** in `.local/`. A public install can
  therefore run the runner against a task set the operator supplies; the
  bundled benchmark tasks are not shipped. This is the settled split, and the
  residual question is only whether a small public sample task set ships
  later (Open Question 3).
- **The agent subprocess contract, so an interactive agent cannot hang the
  run.** The runner invokes the operator's own agent — a third-party program —
  inside a loop of tasks × arms × k repetitions, so it is started with **stdin
  closed** (`stdin=DEVNULL`) and no TTY, with `OPENAI_BASE_URL` and
  `ANTHROPIC_BASE_URL` injected, so an interactive agent fails fast instead of
  blocking. A **`--agent-timeout SECONDS`** bound (default 900) applies per
  repetition; on expiry the repetition is stopped, marked `INVALID` with the
  reason, and the run continues. The spec's `agent` entry is an **argv list**
  with an optional `agent_args` list, so an operator can pass their own agent's
  non-interactive flags (`--yes`, `-y`, `--permission-mode accept`) — **the
  runner never supplies a flag the operator did not write in the spec**, and it
  never runs a shell string.
- **No shell.** The runner executes operator-supplied commands and the spec
  schema is public, so `shell=True` against a spec field is a command-injection
  surface the moment a spec is not operator-authored. The oracle and the agent
  command both run with **`shell=False` and `shlex.split`**. The spec's task
  and oracle fields are documented **trusted-operator-only**, and a spec from an
  untrusted source is refused unless `--allow-untrusted-spec` is passed.
- **Every runner-started proxy binds `127.0.0.1`** on an ephemeral port, and
  the runner refuses to start otherwise: a proxy bound to `0.0.0.0` with
  opt-in auth is an open relay to the operator's provider key.
- **The isolated key never appears in an artifact.** It reaches the runner
  through an environment variable **named** in the spec — the *name* is
  preregistered, the *value* never is — and the spec file, the run record and
  the exported artifact are all free of the key's value. A test greps all three.
- **Three pre-run refusals, each before any money moves.**
  **E3 — a free model pair is refused.** A `:free` cheap target bills `$0`, so
  the bypass arm's "the ledger moved by a non-zero amount" check can never be
  satisfied, every `active` delta is `$0`, and the run spends real money on the
  `off` arm only to return `INDETERMINATE` — for a reason knowable before it
  starts. The spec is refused with `spec.invalid_value`, naming the model,
  **before any spend**.
  **H1 — the `active` arm must not be able to degenerate into `off`.** Three
  independent mechanisms suppress a rewrite and **none of them is a fault**: a
  key whose allowlist excludes the cheap model *suppresses* the switch; `active`
  mode refuses to *start* unless the cheap model is priced and tool-capable in
  the registry; and the router's own per-turn rules may simply never fire. A
  run could therefore complete with every arm "valid" and measure nothing. The
  cheap target, the registry entry and the key allowlist are a **pre-run check**
  (`spec.invalid_value`), the spec carries a **hard minimum routing-coverage
  floor it may not go below**, and the report publishes **per-arm mean cost per
  request next to the coverage figure** so a degenerate run is visible in the
  output rather than merely inferable.
  **E2 — the ceiling is enforced where it can be enforced exactly.** A ceiling
  checked against the lagging counter is not a bound. The runner's proxy
  therefore gets a **real bounded key** (`budget_usd`, `period_days`), and the
  existing reserve-then-settle ledger refuses with **402 before the request is
  forwarded**. The counter check becomes a cross-check, and `budget_events`
  becomes a third, free falsification of the ledger delta. The residual bound
  is stated honestly as **ceiling plus in-flight requests**.
- **Which risks this executor can actually produce.** The Critical risk names
  three mechanisms: cache rebuild, extra turns, and quality regression. A
  real multi-turn agent can produce all three — cache rebuild when a rewrite
  invalidates the prefix cache, extra turns when a cheap model takes a longer
  path to the same fix, quality regression when a cheap model produces a worse
  edit that the oracle then fails. The runner measures all three, and each
  from an instrument that can actually carry it: **cache effects from Tamias's
  own per-request `cached_input_tokens`**, cross-checked against the billed
  per-request cost once the primary instrument is in place; **extra turns from
  the request count per task**; **quality regression from the oracle**. The
  provider's cumulative counter has no cache breakdown at all, so it cannot
  carry the cache measurement. A mitigation for a mechanism the executor
  cannot cause is not a mitigation, so this is stated rather than assumed.

### The upgrade and error contracts

**Schemas are versioned.** The new `price_sheet_hash` column, the run-record
format and the experiment spec schema each carry a version. Existing
upgrades in this package are append-only migrations (`store.py`), and the new
ones follow the same rule: a migration adds a column and never rewrites a
row. **A row with no recorded hash stays `UNKNOWN` and can never silently
become a matching-provenance claim.** A log written by an older version is
readable by a newer one; a run record written by a newer one is refused by an
older one with a clear message, not a crash. Every schema change ships with a
deprecation note and a one-line migration instruction in the CHANGELOG.

**Errors are a contract, not prose.** Each refusal carries a stable,
machine-readable code alongside an actionable human message. The codes this
design needs: `spec.missing_field`, `spec.invalid_value`,
`spend.not_authorized`, `spend.ceiling_exceeded`, `ledger.key_isolation_failed`,
`ledger.unsettled`, `ledger.generation_id_missing`, `arm.identity_mismatch`,
`arm.reset_refused`, `receipt.incomplete`. Every message states **what
happened, which arm and task it happened to, the safe recovery, and the
command to run next** — and never echoes a credential, a prompt, a response or
oracle output.

### The verdict, the exit code and the channel

A verdict is not a runtime failure and not a usage error, so it needs its own
exit code. The repo's documented contract is `0` ready, `1` runtime failure, `2`
usage error, and the new code sits beside it:

```
0  PROMOTE or DO NOT PROMOTE   both are publishable results
3  INDETERMINATE                the run measured nothing publishable
1  runtime failure              the run could not complete
2  usage error                  bad spec, missing --allow-spend
```

**The exit code, the run record's `verdict` field and the printed verdict are
the same value**, and a test asserts it. Without this, a run in which every
repetition was `INVALID` — a run that measured **nothing** — would exit `0`, and
an agent or CI job reading `$?` would read "the measurement succeeded". That is
the worst possible place for it, because `INDETERMINATE` is the outcome the null
branch cares about.

### The promotion output: what happens when the rule says `PROMOTE`

- **The promotion is advisory, never automatic.** The runner writes a
  recommendation into the run record and the report: *"`active` is recommended
  over `static_cheap` for this task set, on these arms, with this model pair,
  under this spec hash."*
- **No configuration is changed by the runner.** It writes no config file, it
  edits no registry, and it changes no default. The operator applies the
  recommendation by editing their own router configuration, which is a
  deliberate act with a reversible diff.
- **The run record carries the promotion state** (`PROMOTE`, `DO NOT PROMOTE`
  or `INDETERMINATE`), the decision rule's inputs, the spec hash, and the
  per-task results, so the recommendation can be re-derived from the record.

## Approaches Considered

### Approach A: Ship the honest meter
Release the receipt, the cap, the guarantee and D1–D3 and F-13; the routing
stays a documented optional capability; no savings claim; the experiment
runner is a later release.
*Effort M · Risk Low.* Reuses `report`, `dashboard`, `budget.py`, and the
offline halves of `credit_ab_check.py` and `shadow_rate_check.py`.
**Pros:** fastest to a public release; every item free; survives a null
result; smallest diff. **Cons:** leaves the one capability nobody else has
unbuilt; the release reads as SmartProxy-lite; advances the cost-saving aim
not at all.

### Approach B: Evidence Mode in the package  *(chosen)*
Approach A's first public release, then a second release adding a three-arm
experiment runner in the package: an immutable `ArmSpec` (`off` / `active` /
`static_cheap`), `tamias experiment run --spec experiment.toml --allow-spend`
and `tamias experiment verdict --run RUN.jsonl` — **not** `experiment report`,
because `report` is already a top-level verb meaning "summarise cost from a
log", and two verbs with one word and two meanings is a trap; `--run` takes a
**path** to a JSONL run record — arm identity proven by the
contract above, a pinned-revision task reset, a preregistered spec hash and
decision rule, a preflight spend ceiling, ledger attribution checks, and no
text stored.
*Effort L · Risk Med.* Reuses the three arms already defined in the private
harness, the ledger reader, `budget.py`'s reserve logic, and `tamias run`'s
command-injection pattern for driving the operator's agent.
**Pros:** the only framing in the landscape nobody occupies; makes Tamias a
decision system; **once D1 is fixed and the runner is verified offline against
the mock upstream**, credits are the only thing between the project and the
answer. **Cons:** the largest build; adds new public surface — a module, two
CLI verbs, a spec schema and a run-record format — to a 992-test package; the
payoff is still a paid run that has not been authorised; if the result is
null, the machinery is the deliverable and the market may not care.

### Approach C: The receipt as a portable artifact  *(re-opened)*
Approach A, plus a signed, self-contained cost artifact — JSONL plus a signed
manifest — that a user can attach to a PR or a bug report, and that a third
party can check against the provider's ledger without installing anything.
*Effort M · Risk Med.* Reuses `store.py`'s schema, `report`, and
`src/tamias/manifest.py`, **which already implements the signing story this
approach was previously rejected for**: Ed25519 signatures over a canonical
byte form, a required `expires`, and a public-key verifier.
**Pros:** an artifact travels where a proxy cannot, which is the strongest
answer to the crowded-category problem; makes "no text at rest" verifiable by
someone who is not the operator; **and the rejected cost — a signing-key
story, its key source, its trust model and its verification path — is already
shipped and paid for.** **Cons:** a third party still cannot fully verify
without the operator's provider credentials, and that reason disqualifies
neither C nor Evidence Mode, since a third party with provider credentials
can check a run's ledger deltas and one without them can check neither; says
nothing about whether routing saves money, so the biggest risk stays open.
**Status: re-opened, and its best idea is folded into release one** as
`tamias reconcile` plus the text-free exportable artifact; the signed variant
waits for a second operator.

## Recommended Approach

**Approach B, sequenced so that Approach A's first public release lands first
and ships first, and the experiment runner follows as a second release.**

B contains A entirely, so choosing B does not cost A. The sequence matters:
the four defects and the guarantee land in a public release that is complete
and honest on its own terms, and the runner follows, once D1 is fixed. That
ordering respects the no-spend constraint — the runner is built and verified
offline against the mock upstream at zero cost — while putting the project one
credit purchase away from the answer it exists to produce.

B is chosen because it is the only approach that can ever produce the number
the stated aim depends on, and because the runner's offline verification is
free. It is rejected in favour of A only if the maintainer decides the release
must be small and uncontroversial; it is rejected in favour of C because C
leaves the central question untouched.

**The unit of value is corrected: the product is the *reconciled receipt*, and
the experiment is one report the tool emits.** Release 1 as originally scoped
computed its cost from the operator's own price sheet — which is exactly the
method the product's problem statement criticises ("every savings dashboard in
this category computes a figure from a price sheet, which is an estimate the
operator supplied"). That incoherence is the first thing to fix, and it is
cheap: the repo already stores the provider's per-request billed cost
separately from the computed one, and `tamias report` already prints
`spent (billed by OpenRouter)`, `computed cost` and
`difference (billed - computed)`. **Release 1 therefore adds
`tamias reconcile`**: a per-request reconciliation of every logged row against
the provider's billed amount, a per-day variance table, a divergence figure, an
unpriced-request count, and a text-free exportable artifact a third party can
check without installing anything. The reconciled receipt is the product; the
A/B becomes a consumer of it, and the receipt stops being an estimate with a
good CLI.

**The public/private split is settled here, not deferred.** The runner module,
the two CLI verbs, the spec schema and the run-record format are **public**
(`src/tamias/experiment.py`). The task fixtures, the oracle implementations and
the benchmark task set are **maintainer-private** in `.local/`, because they
encode operator-specific work. A public install can therefore run the runner
against a task set the operator supplies; the bundled benchmark tasks are not
shipped. The residual question — whether a small public sample task set ships
later — is Open Question 3.

**The null-result branch is written down in advance, because that is what
makes the null safe to publish.** If the paid run returns `DO NOT PROMOTE` —
if adaptive routing loses to simply pinning a cheap model in the agent's own
config — then the next release is **"Tamias as the local, text-free spend
ledger with hard caps"**: a different README, a different demo, and **zero
further experiment machinery**. The router is demoted to a capability, not the
centrepiece. The release one's positioning says this today, in the present
tense, so the plan has a branch for the outcome it most fears. A plan that
only knows how to look good when routing wins looks foolish when it does not.

**There is no signing in this design.** The run record's integrity property is
that **its inputs are hashed into it**: the spec hash, the pinned revision, the
oracle exit code, the ledger deltas and the arm identity evidence are all
recorded, so a run can be re-derived and compared without a cryptographic
signature and without a key-management story. Approach C was rejected in part
for that reason, and re-importing it here would undo that decision.

## Open Questions

Genuinely undecided only.

1. **Is honest metering a buying reason or a hygiene feature?** Nobody in the
   scan reconciles against the ledger, which is an unfilled position — but an
   unfilled position is not the same as a paying one. Free LiteLLM may be
   "good enough" for most users.
2. **What are the assignment unit, the repetition factor `k`, the task count
   and the minimum detectable difference for the three-arm run?** The design
   spec's F-35 leaves them open, and a run without a preregistered answer
   produces a number nobody can trust. The MDD is derived from the offline
   rehearsal's observed per-task variance, and that rehearsal has not
   happened.
3. **Should a small public sample task set ship with the package?** The
   runner is public and the tasks are private, so a public install has no task
   to run until the operator writes one. A tiny, self-contained sample would
   make the one-command claim true for a stranger — at the cost of publishing
   what the private benchmark set is measured against.
4. **What are the fail-open counter's threshold and wording, and does an
   incomplete receipt get excluded from totals?** F-13 is committed as a
   counter surfaced in `tamias report`. The remaining choices are whether the
   counter has a threshold at which the report escalates from a note to a
   warning, what the wording says, and whether a receipt with fail-open events
   in it is excluded from the headline totals rather than reported alongside
   them.
5. **Is `--min-gap` added to `tamias run`, or is the router-config route
   documented as the supported way?** D3's fix is undecided between a flag
   and a documentation change; the flag is more discoverable and the config
   route is more consistent with `serve`.

## Success Criteria

**First public release:**
- Every printed dollar figure is either reconciled, or labelled as an
  estimate, and no receipt line claims a saving that was not measured.
- `tamias report` computes the same saving for the same log regardless of how
  the price sheet was spelled, **and** warns when the sheet's *content* differs
  from the one recorded in the log — not merely when its name differs.
- Every documented budget behaviour — cap breach, per-model sub-cap, RPM and
  TPM windows, refusal of an unpriced model under a money limit, the
  `actual − ceiling` overshoot bound, and a concurrent burst not slipping past
  the cap — is executed against a running proxy and pinned by a test.
- A first-time user goes from a clean install to a routed request using only
  the documentation, with no schema error and no unexplained `UNKNOWN` cost.
- The live candidate sweep can no longer report a ranking it did not measure:
  each arm differs in mode, target or bypass, and each arm's identity is
  proven before its cost is counted.
- A receipt that contains a fail-open event says so.
- `tamias reconcile` reproduces a known billed-vs-computed divergence on a
  recorded log, and the divergence the operator sees is the divergence the
  provider billed.
- The guarantee sentence in the README says the cap is enforced against the
  **computed** cost, and the passthrough exemption is either closed or a
  tested qualification.

**Second release (the experiment runner):**
- The runner exists in the package, is verified offline against the mock
  upstream, refuses to spend without `--allow-spend`, proves each arm's
  identity by the contract above, applies the preregistered decision rule, and
  cannot rank candidates whose observed cost ranges overlap.
- A run's ledger deltas are USD amounts read from the provider's counter, with
  no price sheet anywhere in the comparison.

**The paid run, when the owner authorises it:**
- A per-task net delta against the provider's ledger, with its inputs hashed
  into the run record — **or** a published null, negative or indeterminate
  result. Either is a success; a withheld result is not.

## Where the local cap wins against the provider's own cap

The most likely "no" is "just set a limit in the provider dashboard", and it
must be answered, not dodged. OpenRouter enforces per-key spend caps natively
and reports per-response cost and key usage. For a prospect with a flat
monthly cap on one provider, the local cap is redundant. **The local cap wins
in four places, and only these four:**

1. **Per-model sub-caps.** The provider has none: one budget covers every
   model, so a single expensive model can consume a budget meant for cheap
   work.
2. **RPM and TPM windows.** The provider's quotas bound request volume; they
   are not a token-rate control over a burst.
3. **Provider independence.** The local cap covers BYOK and
   direct-provider spend that never touches the provider's dashboard.
4. **A local record that outlives the provider's dashboard retention**, and
   per-key revocation that applies to new requests only.

**If none of those four is the reason a user is here, the cap is not the
headline of release one — the receipt is.** That sentence is written here so
it is not written later under pressure.

### R3-1 — consistency (blocking)

**Problem**

> Conditions 2 and 4 assign two different outcomes to the same observable event, so the attribution contract cannot be implemented as written. Condition 2 requires the post-arm double read to be equal and invalidates the arm on any movement between the two reads, on the stated ground that movement means 'another workload using the key' that 'falls inside the measured bracket' and 'would be silently attributed to the arm'. Condition 4 then says the opposite for exactly the same event: 'the provider's counter may be delayed or batched', and for that case prescribes re-reading until the counter stops moving, invalidating the arm only if it is 'still moving when the settle window expires'. So on a provider that bills asynchronously - the case condition 4 was written for - the post-arm readings differ and the arm is simultaneously INVALID (condition 2) and to be settled and used (condition 4). The document never says which governs. If condition 2 governs, every arm on an asynchronously-billed provider is invalid, the excluded fraction crosses the preregistered threshold, and the run can only ever return INDETERMINATE: the measurement can never be made with the instrument the design committed to. If condition 4 governs, condition 2's post-arm clause is dead text and the runner must guess. Condition 2's post-arm clause also mis-diagnoses late-billed traffic from the previous arm as concurrent traffic, since condition 4 admits the counter may lag.

**Remedy**

> State the precedence explicitly: make the post-arm read part of the settle loop (the loop terminates on two consecutive equal reads, and the arm is invalid only if the counter is still moving when the settle window expires), and drop the 'must also be equal' invalidity rule for the post-arm read. If the pre-arm read keeps its equal-read rule, say that a pre-arm movement invalidates the arm as concurrent traffic and state how the runner distinguishes that from a late-arriving update of the previous arm's own requests (for example by requiring the previous arm's counter to settle before the next bracket opens).

### R3-2 — completeness (blocking)

**Problem**

> The new repetition structure has no defined relationship to the ledger attribution contract, so the k observations the decision rule now needs have no stated source. The decision rule says each task is run k times per arm, that each (task, arm) cell holds k observations, and that the per-arm range is the [min, max] of those k observations - the range the separation test compares. ### R3-4 — consistency (blocking)
